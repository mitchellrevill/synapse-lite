# Ornata pure spatial mapping

`secbird_core::ornata_spatial` maps an explicitly selected source layout's logical 7×23 RGB frame into a physical 6×22 RGB frame. It opens no files/devices, chooses no locale, reads no hardware identity, and sends no lighting commands. Production code contains no vendor coordinate table; callers supply a bounded layout projection.

`OrnataSpatialMap::from_record(expected_identity, record)` requires an explicit `LayoutIdentity` containing VID, PID, edition and layout. It supports the recovered VID 1532/PID 025D, edition 0 and the 17 packaged layout IDs: 1–12, 15–18 and 20. The record identity must match exactly. There is no default identity or fallback to layout 1. A historical observation of edition 0/layout 6 is not treated as fresh device evidence by this API.

`SourceLayoutRecord` carries declared manifest provenance, dimensions and ordered `MappingEntry` records. Each entry contains logical and physical row/column pairs. The declared digest must equal the recovered source manifest SHA256 `3595e11f1d8778180d1dd6edd2463c8b3b8e446542c5020dc1fa038c67937a93`; dimensions must be exactly 7×23 and 6×22. The pure mapper validates this declaration and the supplied data's bounds. It does **not** authenticate a caller's projection or hash/read the original manifest. The producing asset loader must verify that its projection came from that artifact. Returned `LayoutProvenance` retains the explicit identity, declared digest and source entry count.

Source records require 1–256 entries; 256 is this implementation's allocation/processing ceiling, not a claimed native limit. Every coordinate is validated before a usable map is returned. Unknown identities, mismatched records, wrong digest, reversed/unsupported dimensions, empty/oversized lists and coordinates outside either grid return typed errors. The mapper retains a fixed 132-element u16 physical-to-logical table and bounded metadata, with no heap allocation or frame history.

The source algorithm is preserved directly: initialize every physical index as unmapped, then process the input array in order:

`physical_to_logical[physical_row * 22 + physical_col] = logical_row * 23 + logical_col`.

Duplicate physical destinations keep the **last** source entry, without sorting, blending or averaging. Layout 12 has 119 records for 117 destinations. Its physical (0,21) first names logical (0,22), then (1,14); the latter wins. Physical (3,14) similarly ends at logical (3,15). UK layout 6 has 114 distinct mapped destinations and 18 holes.

`map_frame_into(logical, physical)` requires exactly 161 input and 132 output `Rgb` values. It checks both sizes before any output mutation. Every successful call clears the output to black, then copies mapped logical pixels without changing R/G/B channel order. Holes stay black each frame rather than retaining prior colors. The returned physical row-major frame is suitable as data for the separate canonical Ornata transport; this module never invokes that transport.

Source basis is RzLightingEngineApi_v4.0.55.0.dll SHA256 `cd9fc2a61ff920b9b73e1f5e27632020e2f8586f443e426a875ad3b042b714fa`: parser RVA 30B0 constructs the ordered table (REA `ev_cbdbbef1633198bb007880f00031b9623b469f51ff152ea96f3c409c463f08b3`); mapper 5580 clears/copies RGB triples (`ev_1a8e7c1e4cf16e6b9e304e98f5d86f39933f8c9eb7d3a334bc175526a6f26cbc`); callback 4980 emits the physical dimensions and RGB order (`ev_beb4860f0860aae5a440287b120864e0307b157c0536a0f1cc4863a1ae307deb`). Shipped Ornata writer chunk 2890 SHA256 `1e49e375d27a457dadcf525f2032d66c4d3e7d9330eb34afca279d5633a1b3cd` slices those physical rows unchanged. Native source was analyzed statically and never executed.

For a fresh single-device Basic engine with region 0/orientation 0 and default geometry, the independently recovered zero-LED-dimension fallback gives a 920×280 rectangle with 40×40 cells, preserving logical width 23 and height 7. The source Quick keyboard Wave setting 1 means left and 2 means right; split settings 5/6 and rotational modes remain separate. The pure composition test uses exactly `WaveRegion::new(7, 23, 0, 0, 23, 7)`. A Boolean `counterclockwise: false` is not substituted for an absent field: either Boolean selects a source rotational path.

Seven tests cover all 17 source records against independent colored-ramp RGB bytes, exact UK occupancy, ordered layout-12 collisions, strict identity/provenance/dimensions, coordinate/entry budgets and atomic wrong-frame-size rejection. A separate composition test compares every byte of both complete 25-frame left/right Wave cycles against independently scalar-derived physical frames, verifies all 18 holes stay black, and changes the entire logical padding row to white to prove it has no physical destination.

Fixtures contain numeric layout projections and synthetic static-derived RGB data, not vendor code, SVGs, source input tables or runtime captures. The 6,732-byte ramp fixture SHA256 is `ed3b72aae57cfe0c33cee9ae730cdd55748888fafdcea32b9b461f8a48818572`. The 19,800-byte Wave composition fixture SHA256 is `f855946d0c43ad03a9ec5d29843d54db10cb17d4804adc6107622d727d68ee56`. Provenance and per-layout/per-cycle hashes remain in `tests/fixtures/ornata_spatial.json`.

This unit does not integrate a runtime worker, automatically select a layout, establish live ownership/phase or verify optical placement. Action52 GetCurrentFrame array semantics, nonzero regions, custom positions/orientations, multi-device geometry and alternate source artifacts remain outside this boundary. Source coordinate compatibility and passing byte tests do not themselves prove visible behavior on hardware.
