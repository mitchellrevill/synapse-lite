# Keyboard symbolic packet planning

`secbird_core::keyboard_symbolic_bridge` converts explicit native keyboard fields into a fixed plan containing at most two RZCONTROL packets. It has no sender, driver handle, scheduling thread, OS input API, hardware access, vendor DLL dependency, or synthetic release behavior. The [source macro parser](SOURCE-MACROS.md), [raw packet codec](RZCONTROL-PACKETS.md), and [driver ownership contract](DRIVER-CONTROL.md) remain separate boundaries.

`NativeKeyFlags::new` accepts exactly0..5: ordinary make/break0/1, E0 make/break2/3, E1 make/break4/5. Mixed E0/E1 flags6/7 and unknown bits fail. Scan code bits are preserved; neither a coincident scan code nor its high byte creates an extended prefix. The source parser now accepts the same six explicit flags and derives direction from bit0. Ambiguous imported flag0/1 remains ordinary.

`ExplicitNativeKeyboard` receives a native make code, validated flags, explicit modifier mask, and optional explicit source UnitId. `from_source_event` rejects non-keyboard events and inconsistent public Event direction/flag combinations. The source parser now retains optional modifiers and unitId; explicit source values, including zero, take precedence over the bridge caller's fallback fields. Timers still fail conservatively. Storage retains original JSON separately. See [native keyboard fields](NATIVE-KEYBOARD-FIELDS.md).

Every call to `plan_keyboard_packets` requires a `RoutingIdentity::new(NonZeroU128, unit_id)` with no Default. The opaque token records caller context; it is never a packet routing word, handle, physical identity or proof of ownership. Omitted source UnitId resolves to the proven native fresh-object default0 and records `NativeDefaultZero` provenance. Both this effective0 and any explicit source UnitId must match the caller's routing UnitId; otherwise planning returns UnitIdConflict. Nonzero source UnitId therefore requires explicit Some(unit). Nothing inserts the filter's0xABCD sentinel.

Ordinary packets use routing word0, kind1, UnitId at8, make code at10, raw flags at12, reserved0 at14, translated modifier metadata at16 and zero tail20..31. All numeric fields are little endian. The bridge reuses `rzcontrol_packet` rather than maintaining a duplicate serializer. Metadata uses the recovered numeric map0x400→1,0x200→2,0x100→4,0x40→0x40,0x20→0x80,0x10→0x100; unsupported bits are discarded exactly by that transform, without inventing semantic modifier ownership.

For make code0x1D with flag bit4 set, the first packet is unchanged and the plan contains a conditional second0x45 packet with flags&1 and the same UnitId. Native senders assign translated metadata to a fresh second object and recursively translate it again. Thus the second packet uses `T(T(modifiers)) = (modifiers &0x40) | ((modifiers &0x10)>>2)`, not a copy of the first packet's ExtraInformation.

The plan exposes `first_packet()`, `has_conditional_second()`, and `second_after_first_submission(FirstSubmission)`. A rejected first submission always returns no second packet. Only Accepted exposes the conditional second. This models the submit helper's **boolean acceptance**, not I/O completion; repeated queries on the immutable plan do not track sends or enforce exactly once. There is deliberately no unconditional packet iterator. Native allocation failure can suppress the second object; pure fixed-size construction does not simulate allocator failure or guarantee successful submission.

All plans always report five unresolved runtime gaps: identity validation, endpoint routing, asynchronous completion, cancellation, and held-output ownership. Byte compatibility is not permission or sufficient implementation for live macros. In-flight cancellation, modifier expansion and shared-key references remain incomplete; no blanket release, Win32 fallback, hook or transport is supplied.
