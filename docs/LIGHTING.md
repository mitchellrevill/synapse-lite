# Source lighting intent

Ornata's brightness switch retains both a numeric value and an enabled flag. Turning it off projects zero brightness without replacing its selected effect; turning it back on restores the retained value. A slider edit to zero disables brightness, while a positive edit enables it. The shipped slider accepts all integer percentages 0–100. The separate product shortcut step must not be substituted for this slider step.

`Profile.lighting_settings` retains optional `Brightness` and `SwitchOffLighting` state, including unknown source members. The source names are `brightness.isEnabled/value` and `switchOffLighting.isDisplayOn/isIdleEnabled/idleMinutes`. Despite its name, `isDisplayOn` selects “When display is turned Off”; it is not a read of current display state. Idle minutes remain stored while disabled. Brightness-off disables the policy controls without deleting their flags. `Zone.off` continues to mean effect-off and is not used as the brightness enable flag.

The source fields belong to the named Ornata profile. Synapse import/export preserves their retained values and opaque members. A legacy physical brightness projection remains readable by older Secretarybird clients. Those clients can discard the new intent when they save; that compatibility limitation remains explicit. Old native profiles without typed lighting intent keep their previous application behavior. Direct supported brightness edits synchronize typed intent and its projection.

The full brightness action requires the expected physical device and active profile, checks lighting-control ownership and validates the complete prospective native backup budget before issuing a hardware command. It writes and verifies brightness even when the requested intent is unchanged, so explicitly setting 73 repairs a device that drifted to 30. The separate policy-only action rejects a simultaneous brightness change and sends no HID request. Every preflight refusal restores temporary profile and device-key resolution changes, including legacy bare-PID migration.

Policy retention is not policy execution. Enabled idle/display settings currently produce an explicit unsupported-runtime result on profile activation. Host input-idle detection, display events, temporary suppression, restoration, macro-recorder/OTFM ownership and Windows Dynamic Lighting coordination remain unfinished. The source policies must not be mapped to a device sleep timer or to a different lighting effect.

The current native Lighting page remains a partial generic view; the recovered layout, effects selector, full color editor and policy runtime are not integrated yet. Twelve source quick presets are advertised, but this is not evidence that twelve firmware effects work. Source UI IDs, software-engine IDs and firmware IDs differ. Host effects require frame generation and event/audio/ambient inputs that a firmware effect ID cannot represent. See [firmware readback and its limits](LIGHTING-READBACK.md).

Regression coverage includes all 101 encoded percentage values through the simulator, retained off/on values, effect-off separation, opaque data and explicit deletion, policy-only no-I/O edits, unchanged-value resynchronization, persistence, stale identities/profiles, ownership, budget refusal and rollback of device-key resolution. These tests do not establish new physical brightness/effect workflows. Earlier raw brightness restoration checks remain scoped to their recorded harnesses.
