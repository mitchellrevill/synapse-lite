# Bounded native profile persistence

Native file loading and saving now share the existing interchange resource policy: at most 2 MiB of JSON, 32768 structural tokens and 64 nesting levels. Oversized or excessively structured data is refused with an error; the file is preserved. This is a documented supported-data limit, not proof of compatibility with every larger upstream profile database.

The loader opens the file and reads at most 2 MiB plus one overflow-detection byte before parsing. File growth or misleading metadata cannot bypass that limit. It checks structure before constructing the typed Store, retains unknown fields, accepts the previous repeated UTF-8 BOM form and keeps the existing old-button-name migration. A missing file still produces an empty Store bound to that path. Other failures remain errors rather than silently becoming a replacement default database.

`Store::native_bytes` serializes into a capped writer, validates structural limits, and performs no file operation. Normal output keeps the existing pretty JSON. If formatting whitespace alone exceeds the byte budget, a fresh capped compact serialization is attempted. An exact-limit compact document can therefore remain saveable without dropping opaque data. No unbounded intermediate string is created. The byte budget is a document limit; allocator capacity and the application's whole working set remain separate measurements.

`Store::validate_save` checks that same contract before device operations. Native CLI and server backup exports use the bounded encoder, so a compact boundary file is not expanded into an unimportable native backup. Foreign Synapse export retains its own format/record checks and remains a separate translation boundary.

Save completes serialization and validation before creating directories or touching an existing temporary file. It writes and synchronizes the temporary file, closes it and renames it onto the destination. Refused serialization leaves both the original and any prior temporary evidence unchanged. This is not an interprocess file lock or a guarantee against every filesystem/power-loss condition; simultaneous external writers and unexpected storage failures remain separate recovery concerns.

[Action preflight](ACTION-PERSISTENCE-PREFLIGHT.md) validates exact or conservative possible persisted outcomes before the first SET. Existing mandatory button/onboard recovery snapshots are saved before mutation and remain available after hardware failure. A predictable budget refusal cannot be treated as a successful device change. Filesystem errors after a successful hardware command still require an explicit failure report; this checkpoint does not invent a hardware rollback.

Focused storage tests cover a growing stream's read cap, opaque/BOM/legacy-name round trips, rejection without altering original/temporary files, oversized and node-heavy input, and exact-limit compact persistence. Simulator action tests cover byte/token boundaries, aliases, normalized DPI/stages, aggregate partial-sync bounds and recovery phases. These checks execute no physical device operation and do not replace the broader final RAM/workflow acceptance gate.
